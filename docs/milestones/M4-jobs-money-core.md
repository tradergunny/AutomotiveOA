# M4 — Jobs & money core

The money milestone. Goal: a case's Findings become priced, authorized work — the Advisor groups Findings into Jobs, prices them from the Service Catalog or by quote (Manager can override), records each payer's authorization with its channel, tracks the parts every Job needs, and issues versioned, immutable Quotations printable as a document. No working-status flow, no board, no payments yet (M5/M7); the case now knows *what will be done, for how much, and who approved it*.

**Branch:** `m4-jobs-money-core` · **Gate:** a priced, authorized case with a printable quotation exists.

## Scope (in)
1. **Schema — ServiceCatalogItem, Job, JobAuthorization, PartLine, Quotation, QuotationLine; plus `Finding.jobId` and `Photo.jobId`.**
   - **ServiceCatalogItem**: name (shop-authored free text in the Shop's own language — catalog content is tenant data, never i18n copy), price, `active` flag (deactivate, never delete — Jobs reference it), optional note.
   - **Job**: RepairCase FK (same-shop composite), title (free text; suggested from the grouped Findings or the catalog name), `status` — ship the **full** CONTEXT.md enum now (`PROPOSED / AUTHORIZED / WAITING / IN_PROGRESS / QC / COMPLETED / DECLINED / CANCELLED`) so M5 never alters a Postgres enum, but M4 code only ever writes `PROPOSED`, `AUTHORIZED`, `DECLINED` (the waiting-reason column and all other transitions are M5); `payerType` (`CUSTOMER`/`INSURER`) plus free-text `insurerName` (the Claim FK arrives in M8 per MILESTONES — this is M4's entire insurance surface); nullable `catalogItemId` (set = standard service priced from the catalog; null = quoted bodywork — presence-based, like Finding's zone/checklistItem); nullable `price` (a Job may exist before it is priced; quotation issue and authorization recording both require one); `priceOverriddenByStaffId` (null = no override); nullable assigned Staff; optional note. `@@unique([shopId, caseId, id])` as the target for the same-case FKs below.
   - **Finding** gains nullable `jobId` — composite FK pinning the Job to the Finding's own shop **and case** — a Finding is fulfilled by at most one Job (decision below); grouping = pointing several Findings at one Job.
   - **Photo** gains nullable `jobId` (same shop-and-case composite FK): Job-level progress/after-work shots, uploaded by office staff from the LINE-group relay (CONTEXT.md's accepted manual path). A Photo links a Finding or a Job, never both (app-level validation).
   - **JobAuthorization**: Job FK (same-shop composite), `decision` (`AUTHORIZED`/`DECLINED`), `channel` (`LINE / PHONE / IN_PERSON / OTHER`), optional link to the Quotation version presented, note, recording Staff + timestamp. Append-only — corrections append, never edit.
   - **PartLine**: Job FK (same-shop composite), name, quantity, optional unit cost (internal — decision below), supplier/source, `orderStatus` (`NOT_ORDERED → ORDERED → ARRIVED`), optional ETA date, note.
   - **Quotation**: RepairCase FK (same-shop composite), number + version (decision below), issuing Staff + timestamp, snapshot total. Immutable after create — no update path exists anywhere in the app.
   - **QuotationLine**: Quotation FK (same-shop composite), snapshot fields (title, price, payer) plus a nullable back-link to the live Job (`onDelete: SetNull` — the snapshot must survive anything, including a Proposed Job later deleted).

   All classified in `lib/tenant.ts`; tenant-guard tests extended to every new model and cross-model link.
2. **Service Catalog screen** (`/catalog`) — Manager-only maintenance (CONTEXT.md: maintained per Shop by its Manager): create, edit, deactivate. Advisors get read/pick access in the Job builder only. Role checks server-enforced — the M1 permission stubs become real here.
3. **Job builder on the case** — two creation paths from the Repair Case page (and the Inspection screen's Findings list): (a) select one or more ungrouped Findings → one Job fulfilling them, title suggested, quoted price entered by hand; (b) pick a Service Catalog entry → standard-service Job at the catalog price, price read-only for Advisors. Every Job takes a payer at creation; optional technician assignment (a Staff select — display-only until the M5 board). Jobs are editable and deletable while `PROPOSED`; deleting one releases its Findings back to ungrouped. **Manager price override**: a Manager may set a catalog Job's price away from the catalog entry — recorded via `priceOverriddenByStaffId` and visibly badged; Advisors get no price field on catalog Jobs, server-enforced.
4. **Authorization recording** — per Job, never all-or-nothing on the visit (CONTEXT.md). Staff record the payer's response after it arrives (LINE chat, phone, in person; insurer decisions arrive outside the system): decision Authorized or Declined, channel, optional note, optionally which Quotation version was presented. The Job's status flips accordingly; recorded-by/at shows on the Job. Declined Jobs stay on the case permanently — they are M7's follow-up feed. Mis-records: a Manager-only "revert to Proposed" that itself appends to the authorization history.
5. **Part Lines** — CRUD on a Job: the structured "what this repair needs" list, order status freely editable in M4 (the dashboard that surfaces Waiting (Parts) is M5). No stock, no purchasing ([LATER.md](../LATER.md)) — the system knows what this repair needs and whether it has arrived, nothing more.
6. **Quotations** — an explicit **Issue quotation** action on the case: staff select the Jobs to include (default: all priced, non-declined ones), and the system snapshots titles + prices into an immutable Quotation with lines and a total. The case page lists every version forever; each opens a document view with a print/PDF affordance (decision below), always-light per D-1, Thai-first copy. A staleness hint marks the latest version when the included Jobs' prices or set have changed since issue ("prices changed since v2 — issue a new version?") — issuing is always a human act, never automatic.
7. **Case page integration** — a Jobs section: per-Job rows (title, payer, price with override badge, status chip per D-3, part-line rollup like "2 parts · 1 arrived"), a money summary (total proposed / total authorized — balance due waits for M7's Payments), and the quotation version list. The Inspection screen's Findings list shows each Finding's Job ("→ left-side repaint") and offers group-into-Job for ungrouped ones — the M3 ban on the quotation CTA lifts. Jobs and Quotations follow M3's guard: creatable and editable any time while the case is not `DELIVERED`.
8. **Seed** — extend with a small Service Catalog on the pilot Shop (Thai-named entries: brake pads, engine oil change, coolant flush…) so catalog Jobs are testable on a fresh clone; still idempotent. No seeded Jobs or Quotations — performing the flow is the gate.

All new UI bilingual through the M1 i18n plumbing — payer, channel, order-status, and Job-status labels, validation, empty states, and the staleness hint in both message files. Catalog entries and Job titles are shop-authored data, not i18n copy. Money renders with tabular numerals (DESIGN.md).

## Scope (out — do not build)
- Job working statuses and transitions (Waiting + reasons, In Progress, QC, Completed, Cancelled), the attention-grouped board, internal timeline events (M5). The status enum ships complete, but M4 writes only Proposed / Authorized / Declined.
- Payments, balance due, customer-spending history (M7). The Follow-up worklist that consumes Declined Jobs (M7) — M4 only makes them exist.
- Anything LINE (M6) — quotations are printed and handed over, not sent through LINE.
- Claim records (M8) — payer `INSURER` + free-text insurer name is the whole insurance surface in M4.
- Tax invoices / receipts (ใบกำกับภาษี) and any VAT computation ([LATER.md](../LATER.md)).
- Inventory/stock/purchasing ([LATER.md](../LATER.md)); catalog categories or import — flat list in MVP.
- Tap-to-approve in LINE ([LATER.md](../LATER.md)); technician logins (Phase 2) — Jobs carry a nullable assignee, nothing more.

## Decisions — ruled by the founder 2026-08-26
- **Money representation — approved.** **Integer satang** (THB minor units) in plain `Int` columns — exact arithmetic, no float ever, serializes cleanly through server components (Prisma `Decimal` leaks Decimal.js objects through the stack); `Int4` caps an amount at ~21M฿, plenty for a garage. Entry UI in baht (satang via decimal input), display via `Intl.NumberFormat` th-TH with tabular numerals. **No currency column** — THB is implicit platform-wide in MVP (a column later is additive). **No VAT math anywhere** — quotation totals are flat sums; tax documents are LATER. For the interview checklist: does the pilot shop quote whole-baht, and VAT-inclusive or not?
- **Quotation versioning & numbering — approved.** Each version is its **own immutable row** (Quotation + snapshot lines); nothing is ever edited or deleted, so "kept forever" is structural. One lineage per case: the base number derives from the case reference (RC-1024 → Q-1024) and versions count up per issue; the set of included Jobs is part of the snapshot, so a version documents *the state of the offer at that moment*. A mixed-payer case issues its insurer-subset document as simply the next version — acceptable for MVP, flagged for pilot validation. Issuing is always explicit (the staleness hint nudges; nothing auto-issues).
- **PDF generation — approved: the print-CSS route.** An always-light, print-styled document view rendered by the app itself; "PDF" is the browser's print-to-PDF or the shop's printer. Zero new dependencies, works on Vercel, Thai text uses the app's own self-hosted fonts, and D-1 already frames quotation prints exactly this way; M8's print-styles pass then polishes margins and page breaks. (The rejected alternatives, for the record: `@react-pdf/renderer` would mean a second layout to maintain; headless Chromium is heavy and fragile on serverless.) The document is **Thai-first** — customer-facing like LINE templates — regardless of the staff member's UI locale.
- **Job price vs Part Lines — approved.** A Job's price is the **single customer-facing amount** — catalog price or quote, parts-inclusive (the catalog's "brake pads" price includes the pads); PartLine `unitCost` is the shop's **internal procurement cost**, optional, never auto-summed into the price and never printed on quotations. Cost/margin reporting is a later module. For the interview checklist: does the pilot shop quote labor and parts as separate customer-facing lines? That would make Part Lines quotation-visible and needs remodeling.
- **Job–Finding linkage — approved.** A Finding is fulfilled by **at most one Job** (`Finding.jobId`) — grouping is many Findings → one Job, never one Finding split across Jobs; a Finding's multi-action set ("repair + repaint") stays one Job, per CONTEXT.md's own example. A Job with **zero** Findings is allowed, for customer-requested standard services ("also do an oil change") — CONTEXT.md's "a Job fulfils one or more Findings" describes the inspection path, not a hard constraint; the strict reading would force the Advisor to fabricate a checklist Finding first.

## Done when
Fresh clone → migrate → seed → log in → check in a car (M2) → inspect (M3): two Damage Map Findings down the left side, brakes Needs work. As Advisor: group both left-side Findings into one quoted Job "left-side repaint" with a hand-entered price, payer self-pay; create a catalog Job from the seeded brake-pads entry — its price is locked, editing refused. As Manager: override the brake Job's price → override badge with who. Add a Part Line to the repaint Job (panel set ×1, Ordered, ETA) — the Job row shows the rollup. Issue Quotation v1 covering both Jobs → correct total; open the print view → always-light document, Thai text renders correctly, saves as PDF from the browser. Record the customer's phone authorization on the repaint Job → Authorized, recorded-by/at visible; record Declined on the brake Job → it stays on the case. Create one insurer-paid Job (free-text insurer name) and record its authorization — the insurance path is recordable end-to-end. Upload a relayed progress photo to the Authorized Job — it appears on the Job, not the walkaround grid. Add a mid-repair Finding, group it into a new priced Job → the staleness hint appears on v1 → issue v2; v1 is byte-for-byte unchanged. Everything usable in TH and EN; catalog maintenance refused for the Advisor, allowed for the Manager. Tenant-guard tests — extended to all six new models and the new cross-model links — pass.
