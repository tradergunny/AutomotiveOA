# M5 — Case Board & internal timeline

The movement milestone. Goal: the priced, authorized work M4 created actually moves — Jobs flow through Waiting (with reasons), In Progress, and a real QC gate to Completed; the case flips Ready and gets Delivered; every operational event lands on a staff-only internal timeline; and the dashboard becomes D-2's attention-grouped board. No LINE, no money movement yet (M6/M7); the shop's day is now *visible on one screen*.

**Branch:** `m5-case-board-internal-timeline` · **Gate:** the shop's day is visible on one screen.

## Scope (in)
1. **Schema — CaseEvent (shape per decision 1), `Job.waitingReason`, case delivery fields.**
   - **`WaitingReason`** enum `PARTS / PAINT_BOOTH / TECHNICIAN / OTHER` (CONTEXT.md's fixed set) — new nullable column on Job. Required while status is `WAITING`, cleared on leaving (app-validated; history lives in events). A reason change while Waiting is itself an event.
   - **CaseEvent** — RepairCase FK (same-shop composite), nullable `jobId` (same-case composite, the M4 idiom), typed event enum plus small structured fields (from/to status, waiting reason, note), actor Staff + timestamp. **Append-only**: created complete, never touched again — no update path, no `updatedAt` (Quotation's idiom).
   - **RepairCase** gains nullable `readyAt`, `deliveredAt`, and delivering Staff.
   - All classified in `lib/tenant.ts`; tenant-guard tests extended to the new model and links.
2. **Job transition flow** — server actions enforcing the legal-edge map from decision 2; **no free status dropdown anywhere**. Job-card controls: Start work, Set waiting (reason picker), Back to work, Send to QC, QC pass / QC fail (required reason note — the bounce is internal-only, CONTEXT.md), Cancel (required note; governance per decision 2). Every transition writes its event in the same transaction. M4 code only ever wrote `PROPOSED / AUTHORIZED / DECLINED`; M5 now writes the rest of the enum. Transitions follow the M3/M4 guard: allowed any time while the case is not `DELIVERED`.
3. **QC gate** — `QC → COMPLETED` requires the QC sign-off permission (decision 3): the M1 stub becomes real, server-enforced; the signer lands on the event; never the Job's assigned technician — enforced now even though technicians have no logins, since Staff are promotable to Users later (CONTEXT.md).
4. **Case status** — Ready and Delivered per decision 4: derived Ready flips in both directions, explicit **Mark delivered** from Ready with a confirm. Delivery closes editing — the M3/M4 "while not `DELIVERED`" guards get their first real exercise. Delivered does **not** require zero balance (CONTEXT.md; M7 surfaces the debt instead).
5. **Case Board** (`/`) — replace the M2 minimal list with D-2's attention-grouped dense table. Each open case appears **once**, in its highest-precedence group (decision 4c), with reference, plate + vehicle, contact, age since check-in, the Job status rollup ("2 In Progress · 1 Waiting Parts"), assigned technicians, and — on Waiting (Parts) rows — the part rollup and nearest ETA from M4's Part Lines. The **Balance due** group is M7's (it needs Payments): left out entirely, not stubbed. Delivered cases leave the board (still reachable via `/customers` and case pages).
6. **Internal timeline on the case page** — chronological staff-only feed: event label, actor, time, D-3 hue accents (QC fail red, completion green…). Labels render from **typed event data through i18n keys** — never stored prose — so both locales work; free-text notes are shop-authored data and render verbatim. Nothing here is customer-visible anywhere; the Customer Timeline is M6's composer (ADR-003).
7. **Case page integration** — the header's plain Checked In badge becomes the real thing: case status plus the derived rollup chip; Ready/Delivered affordances; the timeline section; Job cards show current status + waiting-reason chips per D-3.
8. **Seed** — add two technician Staff records (no logins) to the pilot Shop so assignment and the QC never-own-work rule are exercisable on a fresh clone; still idempotent. No seeded Jobs, statuses, or events — performing the flow is the gate.

All new UI bilingual through the M1 i18n plumbing — board group headers, transition controls and confirms, waiting reasons, QC dialogs, event labels, validation, and empty states in both message files.

## Scope (out — do not build)
- Anything LINE, including the Customer Timeline composer (M6) — M5 is the private half only.
- Payments, balance due and the board's **Balance due** group, Follow-up worklist, history views (M7).
- Dashboard update-nudges ("no LINE update in 3 days") — [LATER.md](../LATER.md); automatic customer pings — forbidden by ADR-003 until that ADR is revisited.
- Kanban / drag-to-move — rejected by D-2; case progress is derived, so dragging is meaningless.
- Technician logins / mobile view (Phase 2, [LATER.md](../LATER.md)) — technicians report verbally; office staff drive every transition.
- Claim records (M8). Editing or deleting timeline events — append-only, like JobAuthorization.
- Board configurability: filters, saved views, per-technician boards — the fixed D-2 grouping is the MVP.

## Decisions — ruled by the founder 2026-08-27
- **Internal timeline representation — approved: one append-only `CaseEvent` table.** Every operational event becomes a row written in the same transaction as the mutation it records — including the M4-era actions from now on (authorization recorded, quotation issued, price override). One source keeps rendering and ordering trivial; restating facts that JobAuthorization/Quotation rows already hold is accepted — both sides are append-only, so drift can only ever be a missed write. (Rejected alternative, for the record: composing the timeline at read time from the existing append-only tables plus a smaller status-change table — no duplication, but every future event source becomes another join and ordering splits across tables.) Pre-M5 cases on staging get no backfill: their timelines show a derived "checked in" entry (from `checkedInAt`) and real events from M5 onward. Event kinds: job created / deleted, status changed (incl. waiting reason set/changed), QC pass/fail with note, cancelled, single-step revert, authorization recorded, quotation issued, price overridden, technician assigned/changed, case ready — and its automatic revocation, which both-directions flipping implies — and case delivered.
- **Job transition governance — approved: a fixed server-side edge map** — the app refuses anything not on it, and no free status dropdown exists anywhere. Any User performs the floor transitions (office-driven MVP: the Advisor records the technicians' verbal reports): `AUTHORIZED → IN_PROGRESS | WAITING`; `WAITING ↔ IN_PROGRESS`; `IN_PROGRESS → QC`; `QC → COMPLETED` (QC permission) `| IN_PROGRESS` (fail, required note). **QC is mandatory** — no `IN_PROGRESS → COMPLETED` shortcut, even for an oil change: CONTEXT.md's lifecycle says so, the gate itself is a working assumption the pilot will validate, and making it skippable later is a one-line map change. **`CANCELLED` is Manager-only** (from `AUTHORIZED / WAITING / IN_PROGRESS`, required note) — it terminates payer-approved work. Mis-click recovery: a Manager-only single-step revert (the M4 authorization-revert idiom) back along the path the Job came, itself an event.
- **QC sign-off — approved: Manager-only in M5.** Matches the M1 permission stub and the two-login reality; the "QC-authorized Staff" flag (`Staff.qcAuthorized`, Manager-grantable) is additive later, when a pilot shop shows a dedicated QC person or wants the Advisor signing. Sign-off is performed **in-system by the permission holder themselves** — no recorded-on-behalf-of, deliberately unlike authorization recording. Never the Job's assigned technician (server-enforced now, even though technicians have no logins yet).
- **Case status derivation & board grouping — approved, all three parts.** **(a) Ready is derived, both directions:** when at least one authorization-bearing Job exists (ever Authorized, not Cancelled) and every such Job is `COMPLETED`, the case flips `READY` in the same transaction; a Job authorized after that flips it back automatically (mid-repair discovery while the car awaits pickup). Cases whose work never materializes — everything Declined, or no Jobs — never auto-flip; the explicit **Mark ready** action covers the customer-collects-anyway path. **(b) Delivered is always explicit:** a Mark-delivered action at physical handover, only from Ready; balance may be outstanding. **(c) Board placement is single-group:** first match in D-2's order — any undecided `PROPOSED` Job → Awaiting authorization; else any `WAITING` → Waiting; else any `IN_PROGRESS` → In progress; else any `QC` → In QC; `READY` → Ready for pickup. Open cases matching nothing (just checked in, inspection ongoing, or all-declined) land in the new leading **In assessment** catch-all group — D-2 amended accordingly — so no car in the lot is invisible. (Rejected: multi-placement — double-counts cars; the rollup chip already shows the mix.)

## Done when
Fresh clone → migrate → seed → log in → run the M2–M4 flow to a case with two authorized Jobs (quoted repaint, catalog brakes), a seeded technician assigned to the repaint. As Advisor: Start work on the repaint → In Progress; Set waiting (Parts) → the board files the case under **Waiting** with the reason and the part line's ETA; mark the part Arrived (M4 UI), Back to work, Send to QC. QC pass as Advisor is refused server-side; as Manager: QC **fail** with note "paint mismatch — repaint required" → the Job bounces to In Progress, a red internal event with the note appears on the timeline, and nothing anywhere is customer-visible. Back through QC → Manager passes → Completed. Complete the brake Job the same way → the case flips `READY` by itself (event logged; board group **Ready for pickup**). While Ready: record a mid-repair Finding → group into a priced Job → authorize it → the case leaves Ready automatically; Manager cancels that Job with a note → Ready again. **Mark delivered** → confirm → the case leaves the board, and adding a Job, Finding, or Quotation to it is refused (the M3/M4 guards, finally exercised). An arbitrary status write bypassing the edge map is impossible from the UI and refused by the server. The board shows every open case exactly once under D-2 groups; the timeline reads the whole story in order with actors; group headers, transitions, reasons, and event labels all usable in TH and EN. Tenant-guard tests — extended to CaseEvent and its links — pass. PR opened for founder review.
