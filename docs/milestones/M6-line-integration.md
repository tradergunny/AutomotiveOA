# M6 — LINE integration

The customer-facing milestone. Goal: the shop's day, which M5 made visible internally, gets its curated public half — the Shop connects its own LINE Official Account (ADR-002), a Customer is linked to a LINE identity, and Staff compose and deliberately send LINE Updates with photos and a short note (ADR-003). Every send is recorded as an immutable Customer Timeline entry and shows up on M5's internal timeline as a CaseEvent. Nothing auto-sends, ever; nothing internal auto-publishes. The customer now gets *their half of the story, in the Shop's own voice, through the Shop's own brand*.

**Branch:** `m6-line-integration` · **Gate:** a customer's LINE receives a real update.

## Scope (in)
1. **Schema — `ShopLineChannel`, `LineContact`, `LineUpdate`, `LineUpdatePhoto`, plus three `CaseEventType` values.**
   - **ShopLineChannel** — one row per Shop (`@@unique([shopId])`): encrypted `channelSecret` and `channelAccessToken` (decision 2's envelope format, opaque strings to every other layer), cached `botUserId` / `botBasicId` / `botDisplayName` from the verify call, `verifiedAt`, connecting Staff + timestamps. Never `SELECT`ed into anything that crosses to the client — see decision 2.
   - **LineContact** — a LINE identity seen on this Shop's OA: `lineUserId` (`@@unique([shopId, lineUserId])` — userIds are per-channel, so the same person on two Shops' OAs is two rows), cached `displayName` / `pictureUrl`, `followState` (`FOLLOWING / UNFOLLOWED`), `firstSeenAt` / `lastEventAt`, nullable `customerId` (same-shop composite FK) with `linkedByStaffId` / `linkedAt`. At most one linked contact per Customer (partial unique on `[shopId, customerId]`) — relinking replaces, and the replacement is an event.
   - **LineUpdate** — RepairCase FK (same-shop composite), the recipient **snapshotted**: `customerId`, `lineUserId`, and the Customer's name as sent. `bodyText` exactly as sent (shop-authored, rendered verbatim), `deliveryStatus` (`SENT / FAILED`) set once at creation, `lineRequestId` (LINE's `x-line-request-id`, for support), `errorCode` / `errorDetail` on failure, sending Staff + `sentAt`. **Append-only**: created complete after the API call returns, never touched again — no update path, no `updatedAt` (the Quotation/CaseEvent idiom). A retry is a new row.
   - **LineUpdatePhoto** — LineUpdate FK (same-shop composite), Photo FK, `sortOrder`, and `publicToken` (decision 3): a 128-bit random string, unique, the only key by which bytes leave without a session. Nullable so revocation is a `SET NULL`, not a delete of history.
   - **CaseEventType** gains `LINE_UPDATE_SENT`, `LINE_UPDATE_FAILED`, `LINE_CUSTOMER_LINKED` (decision 4). Adding values to an existing Postgres enum is additive; the migration only adds them and does not use them in the same transaction.
   - All classified in `lib/tenant.ts`; tenant-guard tests extended to the four new models and every new cross-model link. `LineContact.lineUserId` is scoped per Shop by construction — a tenant-guard test asserts two Shops can hold the same `lineUserId` without collision, and that neither can read the other's.
2. **Connect your LINE OA** (`/settings` — the M6 stub becomes real, Manager-only). Paste channel secret + channel access token → **Verify connection** calls `GET /v2/bot/info` (a free call), caches the OA's basic id and display name, and only then stores the credentials encrypted. The page then shows: connected OA name/basic id, a masked credential fingerprint (never the value), `verifiedAt`, the **per-Shop webhook URL** to copy into the LINE Developers console, a short bilingual checklist of what to switch on there (Use webhook **on**, auto-reply messages **off**), Re-verify, and Disconnect (clears credentials; keeps LineContacts and history). Advisors see connection state read-only. This is ADR-002's "connect your LINE OA" onboarding step, and M8's second-Shop dry-run will walk it.
3. **Webhook — the identity intake** (`/api/line/webhook/[shopId]`, public, per decision 1). Verifies LINE's `x-line-signature` HMAC-SHA256 against that Shop's channel secret **before** parsing anything; an unsigned or mis-signed body is a 401 and nothing else. Handles `follow` (upsert LineContact, fetch and cache the display name/picture, `FOLLOWING`), `unfollow` (mark `UNFOLLOWED` — the customer blocked or removed the OA; sending is then refused with a clear reason instead of burning quota on a doomed push), and `message` **for identity only** — the userId and a `lastEventAt` bump; **message content is never stored** and never surfaces in the app (CONTEXT.md: replies are handled by Staff in the OA chat inbox). Returns 200 fast and is idempotent on redelivery. `proxy.ts`'s matcher gains the exclusion; the route is rate-limited by a cheap per-shop guard and never leaks whether a shopId exists.
4. **Linking a Customer to a LINE identity** — an **Unlinked LINE contacts** panel in `/settings` (avatar, display name, first seen, last event) where Staff link a contact to a Customer via the M2 phone lookup, plus the reverse entry point on the Customer page ("link a LINE contact"). Unlink and relink are supported and recorded. A Manager-only **paste a userId** escape hatch exists for the founder's own testing and for a shop that already knows an id. Every link/unlink writes `LINE_CUSTOMER_LINKED` on the cases that Customer is the contact for — see decision 4.
5. **The LINE transport seam** (`lib/line.ts`) — one interface (`pushMessages`, `getProfile`, `getBotInfo`), two drivers behind an env switch, exactly like [lib/storage.ts](../../lib/storage.ts): the **live** driver (fetch against `api.line.me`, the Shop's decrypted token, typed error mapping) and the **fake** driver (decision 5) that writes the exact JSON payload to a local outbox and returns a synthetic request id. Every LINE error the staff can actually hit — invalid token (401), quota exhausted (403), not a friend / invalid userId (400), rate-limited (429), network failure — maps to a distinct bilingual message on the composer, never a stack trace.
6. **Customer Timeline composer on the case page** (ADR-003's human in the loop). A panel beside the internal timeline: a **pre-filled Thai draft** (per-Job status lines derived from the case's current Jobs, in customer-safe wording — "อยู่ระหว่างซ่อม", never "QC failed"), fully editable free text; a photo picker over the case's own photos (walkaround, Finding evidence, Job progress) capped per decision 3; a **preview showing exactly what will be sent**, in send order; and an explicit **Send** with a confirm dialog naming the recipient. With no linked LINE identity, the composer still composes but Send is disabled with an inline explanation and a link to §4; with the contact `UNFOLLOWED`, Send is disabled with its own reason. No draft is ever auto-sent, and there is no scheduling.
7. **Send pipeline + recording** — decrypt the Shop's token, mint publication tokens for the chosen photos, build the message array (text + images), call the transport, then write `LineUpdate` + `LineUpdatePhoto` rows + the `CaseEvent` in one small transaction (ordering and its accepted risk: decision 4). Failures record a `FAILED` row with LINE's error and stay retryable — the composer keeps the draft.
8. **Public photo delivery** (`/api/line/photo/[token]`, decision 3) — the second and last unauthenticated route: resolves a live publication token to its Photo, streams the bytes with immutable cache headers, 404s on an unknown or revoked token, and leaks no case, customer, or shop identifier in the URL or the response. Excluded from `proxy.ts` alongside the webhook. `lib/storage.ts`'s comment — bytes only leave through the authenticated route — gets its exception written down precisely, not quietly widened.
9. **Customer Timeline display on the case page** — chronological, staff-visible, showing each sent Update as the customer received it (Thai body, photo thumbnails, sent-by, time) and failed attempts marked as internal-only. Side by side (tabbed below `sm`) with M5's internal timeline, visibly the *other* narrative. Delivered cases keep their Customer Timeline read-only, like everything else.
10. **i18n & seed** — all staff-facing UI bilingual through the M1 plumbing: settings, the webhook checklist, contact linking, composer labels, confirms, every LINE error, empty states. The **draft template and its status wording are Thai-first data**, authored once and not translated to the staff's locale (the quotation-document precedent, DESIGN.md). Seed stays idempotent and seeds **no** LINE channel, contact, or update — connecting, linking and sending is the gate. `.env.example` gains the credential key and the transport switch; README gains a short "LINE in dev" section; [docs/LINE-SETUP.md](../LINE-SETUP.md) walks a non-technical owner through creating the OA and connecting it.

## Scope (out — do not build)
- **Anything that sends without a human pressing send** — forbidden by ADR-003 until that ADR is explicitly revisited. No "car is Ready" pings, no reminders, no scheduling, no retry daemon.
- **Dashboard update-nudges** ("no LINE update in 3 days") — the ADR-003-compatible mitigation, but [LATER.md](../LATER.md), not M6.
- **LIFF / tap-to-approve, LINE Login, rich menus, quick replies, liff-based customer views** ([LATER.md](../LATER.md)). M6 adds no LINE Login channel.
- **Ingesting replies into the system**: message *content* is never read, stored, or displayed. Replies live in the OA chat inbox (CONTEXT.md). The webhook takes identity and nothing else.
- **Flex Messages / message templates as a feature** — plain text + image messages only; a template editor, per-Shop message branding, and Flex layouts are later.
- **Broadcast, multicast, or any send not addressed to one Customer about one Repair Case.** The Follow-up worklist's sends are M7's; customer-level (case-less) Updates arrive with it.
- **Payments, balance due, history views, Follow-up worklist** (M7). **Claim records** and the **case-page density pass** (M8). The **always-open add-part form** — its own follow-up PR, not folded in here.
- Message-quota dashboards, delivery-receipt polling, LINE's insight APIs, credential auto-rotation (M8's deploy guide covers rotation procedure, decision 2).

## Decisions — ruled by the founder 2026-08-27
All five approved as recommended, plus both ADRs.

- **Customer ↔ LINE identity — approved: webhook identity intake + staff-driven linking.** The constraint is hard and worth restating: a push needs a LINE `userId`; no API turns a phone number into one; a userId is per-OA and is **not visible to the customer anywhere in the LINE app**, so nobody can read it out to the advisor. Exactly two sources exist — a webhook event from that OA, or LINE Login/LIFF — and LIFF is deferred ([LATER.md](../LATER.md)). **So M6 is forced toward webhooks**, and "manual userId capture" survives only as a Manager-only paste field for founder testing, never as a customer path. `follow` events catch new friends; **`message` events are ingested for identity only** — otherwise every customer who friended the OA before it was connected is permanently unreachable. Content is never read, stored, or displayed. Accepted costs: the app gains its first public route (signature verification is the entire security boundary, and it is tested like one); onboarding gains a webhook-URL paste on top of ADR-002's existing friction; linking is a human match against nickname-and-emoji display names, mitigated by showing the linked name and avatar on the Customer and in the send confirm; coverage is not total, so "no linked identity" is a normal, explained state in the composer, not an error. Per-Shop webhook URL (`/api/line/webhook/[shopId]`) — the shop is known *before* verification, which a single shared endpoint cannot manage without first trusting the body's `destination`; the shopId in the URL is not a secret and confers nothing without a valid signature. **Recorded as [ADR-005](../adr/ADR-005-line-identity-via-webhook.md)**, which also carries the CONTEXT.md amendment: no message content flows back; identity does. (Deferred, additive on top: the claim-code auto-link — it removes mismatch risk but requires matching message *text*, so it waits for evidence that mismatches are actually common.)
- **Channel-credential encryption — approved: AES-256-GCM in-app, key in the environment. Recorded as [ADR-004](../adr/ADR-004-line-credential-encryption.md).** Node's built-in `crypto`, no new dependency, identical on Vercel and self-host. Stored as `v1:<iv>:<tag>:<ciphertext>`, base64url, with **AAD bound to `shopId` + field name** so a ciphertext lifted from one Shop's row cannot be replayed into another's — the composite-FK reflex, applied to bytes. Key is 32 random bytes in `LINE_CREDENTIALS_KEY`: the same trust tier as `AUTH_SECRET` and `DATABASE_URL`, the ones already there. Handling rules matter more than the cipher: decryption only inside `lib/line-credentials.ts`, only on the server, only at verify/send time; no DTO, server-component payload, or log line may carry plaintext (the settings page renders a masked fingerprint and never fetches the value); a missing or malformed key **disables LINE features with a clear message instead of crashing**, so a fresh clone still boots and every earlier milestone still runs. Rotation is additive by construction (`v1:` prefix + a `LINE_CREDENTIALS_KEY_PREVIOUS` read-fallback); the procedure is M8's deploy guide. Stated plainly: this defeats a leaked database dump or backup — the realistic threat — and does **not** defeat code execution or env access, because the server must be able to decrypt in order to send at all. (Rejected: a managed KMS — real key isolation, but its own credentials then live in the same env, so the boundary moves one hop for a cloud account, a network round-trip on the send path, and a new failure mode; revisit at the first customer security review.) Sub-decision approved: **paste channel secret + a long-lived channel access token** — fewest concepts for a non-technical owner. Issuing short-lived tokens ourselves is hygienically better and comes later; the storage shape is identical either way.
- **Photos to LINE — approved: per-publication capability URLs that never expire.** The constraint: LINE image messages carry `originalContentUrl` + `previewImageUrl` and **LINE's own servers fetch them** — there is no upload endpoint — so the session-only `/api/photos/[id]` returns 401 and the customer sees a broken message. When Staff attach photos and press send, each chosen Photo gets a 128-bit random `publicToken` and a second public route streams those bytes with no session. Properties: **no photo is public until a human published it** (CONTEXT.md's rule, enforced structurally); one copy of the bytes and one storage driver; no case, customer, or shop identifier in the URL; revocation is nulling the token. The trade-off, chosen deliberately: this is a capability URL — whoever holds the link sees that one photo until it is revoked — and the alternative, a signed expiring URL, eventually breaks images in the customer's own chat history, because LINE does not cache fetched images forever. **A repair history the customer can scroll back through is worth more to a garage than a lapsing link**, and the photo is already forwardable from that chat. (Rejected: copying bytes into a public Blob store — least routing work, but it forks photo storage into two lifecycles and makes "public" a property of the file rather than of a human's send decision.) Two staff-visible consequences follow from LINE's own limits, both accepted: **a cap of 4 photos per Update** (one push carries at most 5 message objects; 1 text + 4 images), and **JPEG/PNG only** — M2's downscale emits JPEG, but its fallback passes originals through, so the picker filters the rest and says why; server-side conversion is a later, larger change.
- **What a send records, and the internal timeline — approved: an immutable snapshot, and yes to the CaseEvent.** `LineUpdate` stores the payload **as sent** — body text verbatim, ordered photos, recipient userId and name at that moment — not a recipe for re-rendering it, so a later Job rename, reprice, or relink cannot quietly change the record of what the customer saw. That is the QuotationLine / `CaseEvent.jobTitle` idiom already in the schema. **Failures record too** (`FAILED` rows carrying LINE's error code and `x-line-request-id`), so "did we ever actually tell them?" is answerable months later; a retry appends a new row and the Customer Timeline renders only what was delivered. Sending writes `LINE_UPDATE_SENT` / `LINE_UPDATE_FAILED` on the internal timeline per M5's ruling 1 — **this does not violate ADR-003**, which forbids an internal event *triggering* a customer message; a human's message *causing* an internal note is the safe direction. The entry is a typed, i18n'd label ("Ann sent a LINE update · 3 photos") linking to the Update; the Thai body stays on the Customer Timeline. Linking an identity is likewise an event (`LINE_CUSTOMER_LINKED`). **One accepted risk, stated rather than hidden:** the LINE call is a side effect that cannot be rolled back, so the order is **send, then record in one small transaction** — if the database fails in that window, the customer received a message the system has no record of. Writing a `PENDING` row first cannot close the window either (the process can die between call and update) and costs `LineUpdate` its immutability. Transaction kept minimal, failure logged loudly. Sub-decision: `LineUpdate.caseId` stays **required** — a nullable FK would weaken the same-case pin for zero present benefit; M7's case-less Follow-up sends widen it or take their own path, as a known seam.
- **Verifiability — approved: the storage.ts pattern applied to messaging, plus one live pass.** With no credentials configured (or `LINE_TRANSPORT=fake`), a **fake transport** writes the exact JSON payload it would have posted to `.data/line/outbox.jsonl` (gitignored) and returns a synthetic request id; everything else runs for real — the LineUpdate row, the publication tokens, the CaseEvent, the Customer Timeline. The verification surface is therefore the app itself, plus `cat`-ing the outbox for the literal payload and pasting a photo URL from it into a logged-out browser. For the inbound half, `npm run line:simulate -- follow|message|unfollow` HMACs a sample body with the configured channel secret and POSTs it to the dev server — **no tunnel, no OA, no fees** — and signature verification carries its own unit tests (valid, tampered body, wrong secret, missing header). The honest limit: this proves our side of the wire, not LINE's rendering, friend/block behavior, or Thai text wrapping. **Hence one manual live pass by the founder** on a free-plan OA with their own account as its only friend — a handful of pushes, well inside the free monthly allowance — which is what satisfies MILESTONES' "a customer's LINE receives a real update". Setup is walked step by step in [docs/LINE-SETUP.md](../LINE-SETUP.md).

## Done when
**Fresh clone, no LINE account (fake transport):** clone → install → migrate → seed → log in as Manager → `/settings` shows LINE not connected, and every earlier milestone still works. Paste a random access token → **Verify is refused** with a readable error (the fake transport refuses anything not prefixed `dev-`, exactly as LINE refuses a bad token). Paste `dev-token` → connected, showing the stand-in OA's name, credential fingerprints, and this Shop's webhook URL. `npm run line:simulate -- follow` → the contact appears under **Unlinked LINE contacts** with its display name; match it to the seeded pilot Customer by phone lookup → the link shows on the Customer, and `LINE_CUSTOMER_LINKED` lands on their open case's internal timeline. Run the M2–M5 flow to a case with one repaint Job In Progress and a Job photo attached. Open the Customer Timeline composer: the Thai draft is pre-filled with customer-safe status wording (nothing resembling "QC failed" appears anywhere), edit it, attach two photos, preview shows exactly the text and images in send order, a fifth photo is refused with the cap explained, a WebP photo is filtered out with its reason. Send → confirm names the recipient → the Update appears on the Customer Timeline as sent, `LINE_UPDATE_SENT` appears on the internal timeline, and the outbox line contains the literal payload. Copy a photo URL from the payload into a logged-out browser → the image loads; `/api/photos/[id]` for the same photo still 401s. `npm run line:simulate -- unfollow` → Send is disabled with the unfriended reason. A webhook POST with a tampered signature is refused 401 and writes nothing. Unlink the contact → Send is disabled with the not-linked reason and the composer still composes. Mark the case delivered → the Customer Timeline is read-only. Everything usable in TH and EN; Thai-first customer copy stays Thai in both. Tenant-guard tests — extended to the four new models, including two Shops holding the same `lineUserId` — pass, as do the credential-envelope, signature-verification, fake-transport and draft tests.

**Live pass (founder, one real OA — on the deployed staging URL, since LINE must reach both the webhook and the photo links over the internet; [docs/LINE-SETUP.md](../LINE-SETUP.md) walks every step):** connect a free-plan LINE OA in `/settings` → Verify succeeds and shows the OA's real name → paste the webhook URL into the LINE Developers console → add the OA as a friend from your own LINE account → the contact appears in the inbox → link it to a Customer → compose and send a real Update with two photos → **the message arrives in LINE**: Thai text renders correctly, both photos display, and tapping a photo opens it full-size. The internal timeline records the send; nothing was ever sent that a human did not press send for. PR opened for founder review.
