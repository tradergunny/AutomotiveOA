# M3 — Inspection

The examination milestone. Goal: on an open Repair Case the Advisor runs the Inspection — taps body zones on the Damage Map (artwork chosen by the Vehicle's `bodyType`) and flags Service Checklist items — producing photographed Findings that persist and can keep arriving mid-repair. No Jobs, no pricing, no quotations yet (M4); the case now *knows what's wrong with the car*, with evidence.

**Branch:** `m3-inspection` · **Gate:** an inspection stores tappable-zone Findings with photos.

## Scope (in)
1. **Schema — Finding, plus `Photo.findingId`.** Finding: RepairCase FK (same-shop composite per the M2 idiom), `source` (`DAMAGE_MAP`/`CHECKLIST`), `zone` (canonical zone id, map findings), `checklistItem` (canonical item id, checklist findings), `damageTypes` (multi: `SCRATCH`/`DENT`/`CRACK`/`BROKEN`), `condition` (`DUE_SOON`/`NEEDS_WORK`, checklist findings), `proposedActions` (multi: `REPAIR`/`REPAINT`/`REPLACE`/`SERVICE` — CONTEXT.md's set; the mockup's "repair + repaint" chip = two values), optional note, recording Staff + timestamp (mid-repair additions stay distinguishable). Severity is **derived** (crack/broken ⇒ severe), never stored. Multiple Findings per zone are allowed — a hidden crack found mid-repair behind an already-scratched bumper is a second Finding, not an edit. Photo gains nullable `findingId` with a composite FK pinning the Finding to the photo's own shop **and case** (DB-level, M2 defense-in-depth style). Both classified in `lib/tenant.ts`; tenant-guard tests extended.
2. **Damage Map component** — the unfolded five-view sheet (top centered, left/right profiles, front/rear faces) from the approved mockup; artwork per decision below. The case's `Vehicle.bodyType` selects sedan/pickup — the mockup's body-type toggle was a mockup affordance and does not ship. Zones are tappable and keyboard-accessible (the mockup's tabindex/aria/focus pattern); marked zones show severity hatch (amber minor / red severe per D-3) + a per-zone Finding-count badge; legend + hint line; strokes theme-aware. Small screens per DESIGN.md: pinch-zoom plus tap-to-expand a single view.
3. **Service Checklist** — the second capture surface: fixed item list (decision below), tri-state per item (OK / Due soon / Needs work). Due soon/Needs work creates or updates that item's checklist Finding; OK removes it. On-screen checklist state derives from stored Findings — no separate state table (decision below).
4. **Finding editor** — tap a clean zone → Finding created and opened; tap a marked zone → that zone's Findings, with add-another. Edit damage types, proposed actions, note; attach photos: camera capture or file pick, client-side downscale reused from M2 check-in, thumbnails with remove. Removing a Finding removes its Photo rows (storage bytes orphan, same as M2's aborted-check-in case — accepted, cleanup is a later chore).
5. **Inspection screen** (`/cases/[id]/inspection`) — mockup layout: map left; Findings list + Checklist right; summary bar ("N findings · M photos"). Header: back to case, reference, plate, vehicle, contact (no waiting/ETA chip — that's M4/M5 data). No "Create quotation" / "Send LINE" buttons yet (M4/M6). Reachable from the Repair Case page; Findings can be added/edited any time while the case is not `DELIVERED` (CONTEXT.md's mid-repair rule; M2 never writes DELIVERED, but the guard ships now).
6. **Repair Case page integration** — an Inspection summary section (counts by severity + flagged checklist items, last-recorded time, link to the screen). The walkaround photo grid now shows only case-level photos (`findingId` null); Finding photos render with their Findings.
7. **Seed** — unchanged; no seeded Findings (performing an inspection is the gate).

All new UI bilingual through the M1 i18n plumbing — including all zone labels, checklist items, damage types, actions, legends, hints, and empty states in both message files.

## Scope (out — do not build)
- Grouping Findings into Jobs, pricing, authorization, quotations (M4) — the quotation CTA stays off this screen until then.
- Case status transitions, board changes, internal timeline events (M5). LINE anything (M6). The Follow-up worklist that consumes wear Findings (M7) — M3 only stores what M7 will read.
- Technician-shot photos / LINE-group relay (Job-level, M4+); per-Job QR upload ([LATER.md](../LATER.md)).
- Body types beyond sedan/pickup; per-Shop checklist editing; sub-zone granularity (door-edge, bumper-corner); free-position damage pins at arbitrary x/y — zones only in MVP; drawing/annotation on photos.

## Decisions — ruled by the founder 2026-08-26
- **Damage Map artwork authoring — approved with an amendment: keep the programmatic React SVG, but deeply refine it.** The M0 mockup's geometry is the starting reference, **not a 1:1 port**: improve the vehicle silhouettes, proportions, and panel details; make zone boundaries follow real panel cut lines; and refine the interactions. Still a typed in-repo data module (zone id → shape, per body type) plus decor paths rendered as one React SVG — DESIGN.md's "in-repo, stroke-based, theme-aware, no external assets" holds; one source keeps artwork, tap targets, and the zone registry in lockstep.
- **Body-zone taxonomy — approved.** The **mockup's 32 zone ids** are canonical (single source for artwork, validation, and label keys): front/rear bumpers, grille, hood, windshield, roof, rear glass, headlights + taillights (L/R), front fenders (L/R), four doors, sills (L/R), mirrors (L/R), four wheels — shared; trunk + rear quarters (sedan-only); bed, tailgate, bedsides (pickup-only). Stored as a **string validated against the registry**, not a DB enum — a third body type later is code + copy, not a migration. Wheels are one zone each (tire+rim), glass is windshield/rear only (door glass counts as the door). Damage types scratch/dent/crack/broken; severe = crack or broken (red hatch), else minor (amber) per D-3.
- **Finding photos reuse the M2 photo plumbing — approved.** **One Photo table, one serving route**: nullable `findingId` (composite FK enforcing same shop *and same case* at the DB), `shopId/caseId/uuid` storage keys unchanged, `/api/photos/[id]` untouched — it is already level-agnostic, session-gated, and tenant-checked. Walkaround = photos with no `findingId`. Upload timing: incremental — each Finding saves as captured and its photos upload immediately (server action reusing the M2 downscale), so a mid-inspection tab close loses nothing.
- **Service Checklist content & OK persistence — approved.** Fixed in-code list for MVP: engine / engine oil, transmission, brakes / pads, tires & suspension, battery, lights, air-con, fluids (coolant, brake, washer) — renaming later is copy, not schema. **OK is not persisted** — only Due soon / Needs work become Findings (what M7 follow-ups read); there is deliberately no per-case proof-of-check record. Revisit only if the pilot shop needs one for handover disputes.
