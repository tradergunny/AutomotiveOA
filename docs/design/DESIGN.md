# DESIGN.md — UI Guidelines

Source of truth for look, feel, and frontend conventions. Conceptual language lives in [CONTEXT.md](../../CONTEXT.md); this file is about how the product looks and is coded.

## Stack & structure (locked)

- **Next.js + TypeScript + Tailwind CSS + shadcn/ui** project structure.
- Components: `/components/ui` (shadcn primitives), `/components/blocks` (composed blocks). `cn()` helper from `/lib/utils`.
- Icons: **lucide-react** only.
- Reference artifact: [reference/features-10.tsx](reference/features-10.tsx) — pasted by the founder from their prior project family ("UFC project" style); its conventions govern. Integration of reference components happens at scaffold time, not before.

## Aesthetic: dark technical / bordered

Rules extracted from the reference:

- **Dark-first**, zinc-based neutral scale, shadcn CSS-variable tokens (`--background`, `--muted`, `--primary`…).
- **Sharp geometry**: `rounded-none` on structural surfaces (cards, panels). No soft radii on structure.
- **Thin borders carry the structure**: 1px solid for primary edges, **dashed** for secondary separations (`border-t border-dashed`).
- **Corner-tick decorator** (the signature): 2px `border-primary` brackets on the four corners of key cards.
- **Hatch fills**: 45° `repeating-linear-gradient` stripes for texture/status patterning.
- **Radial-gradient veils** to fade imagery into the surface.
- **Label rows**: `size-4` lucide icon + `text-muted-foreground` caption; large `font-semibold` statements for headings.
- Density: information-dense but calm — this is an operations tool, not a marketing site.

## Typography (proposal — veto welcome)

- Thai-capable pairing at matched weights: **IBM Plex Sans Thai** (or Noto Sans Thai) alongside a matching Latin face (IBM Plex Sans / Geist).
- Tabular numerals wherever money or counts column up (estimates, part lines, balances).

## Language

- **Bilingual TH/EN from day one.** Every user-facing string goes through i18n keys (e.g. next-intl); per-User locale toggle; no hardcoded copy anywhere, including validation and empty states.
- Customer-facing LINE message templates are authored in Thai first.

## Damage Map

- **One unfolded sheet**: top view centered, front/rear/left/right arranged around it — traditional insurance damage-sheet layout. Staff read all visible body damage at a glance; no view switching.
- All exterior zones tappable: bumpers (F/R), grille, hood, roof, boot/bed, each door, each fender/quarter panel, wheels, mirrors, windshield/rear glass, lights.
- Marked zones show state: count badge + severity tint; hatch fill for marked areas (fits the aesthetic).
- Small screens/tablet: pinch-zoom, plus tap-to-expand a single view.
- **Body types in MVP: sedan + pickup.** `Vehicle.bodyType` selects the artwork; zone names stay identical across body types.
- SVG is authored in-repo as a **programmatic React SVG** — typed geometry data (zone id → shape, per body type) plus decor paths; stroke-based, theme-aware, no external asset dependency (D-5).

## Resolved design decisions

- **D-1 Theme: dark-only MVP.** One mode, polished properly. Quotation PDFs remain a separate always-light print artifact. Light mode stays reachable later via shadcn tokens.
- **D-2 Case board: attention-grouped list.** Dense table grouped by what needs a human: In assessment · Awaiting authorization · Waiting (with reason) · In progress · In QC · Ready for pickup · Balance due. Each open case appears in exactly **one** group — the first that matches (M5 ruling); In assessment is the leading catch-all so a just-checked-in car is never invisible. **Balance due** (M7 ruling) holds **delivered** cases still owed money — the one exception to open-cases-only: a delivered case stays on the board, rendered for money rather than work (split balance in red, days since delivered), until its balance clears; Ready rows show the amount to collect at handover. No kanban — Repair Case progress is derived, so drag-to-move is meaningless.
- **D-3 Accent: racing amber-orange.** Starting token: `--primary` ≈ Tailwind orange-500 (`#f97316`), tunable on sight. Corner ticks, CTAs, and active states carry it. Status hues stay conventional: green = done/authorized, amber = waiting/attention, red = declined / QC-fail / overdue balance, blue = in-process (In progress, In QC) — the accent itself is never a status hue. Damage Map severity tint uses the same palette: amber hatch = minor (scratch/dent), red hatch = severe (crack/broken). (Founder may still supply exact UFC-project tokens to override.)
- **D-4 Name: AutomotiveOA** — spelling fixed from the folder's "Automative". Wordmark set in the technical style until a real logo exists; the OA suffix keeps the LINE Official Account association.
- **D-5 Damage Map artwork: programmatic React SVG, refined beyond M0** (founder ruling, 2026-08-26). The M0 mockup's five-view geometry is the starting reference, not a port target: M3 improves silhouettes, proportions, panel details, and zone boundaries (real panel cut lines), and refines the tap/hover/keyboard interactions — while staying a typed in-repo data module. No vector-tool exports, no third-party art.
- **D-6 Repair Case page is stage-led** (founder ruling 2026-08-27). The page headline is the case's **Stage** (CONTEXT.md) rendered as a **stage spine** — a one-line stepper `Assessment → Authorization → Work → Ready → Delivered` with the current stage lit (Waiting/In progress/In QC light "Work" with the specific state written beneath, e.g. "waiting — parts"; Balance due lights "Delivered" with the owed amount beside it) — plus a derived **next-action strip** — one primary action, at most one secondary. In assessment cascades (no Findings → Open inspection; ungrouped Findings → Group into Jobs; unpriced Jobs → Set prices); Awaiting authorization offers Record authorization, with Issue quotation suggested while no Quotation covers the Proposed Jobs — the professional path, never a gate; Waiting shows the blocker itself ("2 parts due Aug 30") instead of a button; Ready and Balance due lead with the money to collect. The header carries stage + one money line only: the lifecycle badge and per-status rollup chips leave the header, the rollup moving into the Jobs section as detail. The strip is a suggestion, never a wizard — Jobs proceed independently and every action stays reachable. Board and case page speak the same Stage vocabulary.
- **D-7 Job cards are records, not forms** (founder ruling 2026-08-27). A card renders read-only, and only what its status warrants: Proposed = the offer (price, payer, authorize/decline); Authorized/Waiting/In progress/QC = the working view (technician, parts + ETAs, transitions, photos); Completed = a receipt (what, who, price, photos — no inputs); Cancelled/Declined = one quiet line with the reason. Empty scaffolding never renders — no headings over nothing, just a small add affordance where adding makes sense. Field changes live behind an explicit per-card **Edit** toggle; **actions are not edits** — status transitions, authorization recording, and part-arrival keep always-visible controls. Parts table: fully spread while the Job is active (refining the earlier always-open ruling), one summary line once terminal.
- **D-8 The quiet rulebook** (founder ruling 2026-08-27). A colored chip means exactly one thing: a **workflow state** (Stage, Job status, part order status, authorization state) — at most one chip per list row; counts and metadata are plain sentences with at most a tinted word ("2 findings — 1 **severe**, 1 minor"). The all-caps eyebrow-label-over-every-field idiom retires: where a value needs naming, quiet muted label–value pairs; self-evident values (฿ amounts, names in known slots) go unlabeled. Real type steps (page title > section title > body > meta) and air at section seams — density lives in tables, not everywhere. Dark-only (D-1) reaffirmed against a light reference: founder's 2026-08-27 "ClaimTrack" screenshot contributes its *organization* (one chip per row, calm label–value pairs, whitespace rhythm, per-vehicle visual identity), explicitly not its light/rounded skin.
- **D-9 Cases wear the car's face** (founder ruling 2026-08-27). Board rows and the case page header carry a small photo thumbnail of **the actual vehicle** — first check-in walkaround photo, no new capture flow — falling back to a plain body-type icon when none exists yet. Real photo over brand logo: it distinguishes three same-model cars in the yard, and no logo asset set to license or maintain.
- **D-10 Case page skeleton: fixed order, stage-aware shrinking** (founder ruling 2026-08-27). One order, always: **Header → Inspection → Jobs → Money → Customer Updates → Activity**. The header absorbs the old Vehicle/Contact cards — car photo, plate, make/model/color, contact name + phone, stage spine, next action, one money line; secondary identity detail (province, odometer, primary-vs-contact) goes small or lives on the linked pages. The walkaround photo grid folds into the Inspection area. Sections never reorder; a section irrelevant to the current Stage collapses to one quiet line (Inspection once work takes shape; Money until Ready/Balance due; Activity always opens as "last event" + expand). Tabs and stage-based reordering rejected: fixed geography preserves muscle memory, shrinking provides the focus.
- **D-11 Findings are accepted, then they stop being forms** (founder ruling 2026-09-01). A Finding renders as an open form while the advisor keys it in and folds to a single line the moment they press **Accept**: zone, what is wrong, what we will do, the note, a photo count, and the Job it feeds. Accepting is a status flip, never a save — every field persisted the moment it was tapped, so an interrupted inspection loses nothing either way. Accept requires a proposed action: confirming means "this is work we intend to register", and an empty proposal registers nothing. Only accepted Findings are offered for grouping into Jobs, and the assessment cascade (D-6) sends the advisor back to the inspection while any Finding is still unaccepted rather than to a grouping step with nothing to group. Reopening is an explicit **Edit**, which un-accepts — the same records-not-forms shape D-7 gives Job cards. The source eyebrow (FROM MAP / FROM CHECKLIST) retires under D-8; severity moves to a coloured left edge on the row reusing the Damage Map's amber/red (D-3), and the Job chip renders only when the Job is named something other than the zone itself.
- **D-12 One zone, one tile — and the row shows the evidence** (founder ruling 2026-09-01). Findings collect by the place they describe: each zone or checklist item is a **raised tile** on the Findings panel (`surface-2`, own border, real air between tiles), titled once with the zone name and counted when it holds more than one entry, so a second dent on the hood reads as another line of the same place rather than a new finding. Hairlines alone could not carry that on a near-black card. Entries inside a tile are numbered only where there is something to tell apart. An accepted entry leads with its **photo thumbnail and its note**, with damage and action demoted to a second line: two scratches on the same panel print identical taxonomy, and the note and the photo are the only things that actually differ. Where there is no note the damage takes the top line — "no note" is not worth a row (D-7, empty scaffolding never renders). Severity is painted as a bar on the tile's left edge rather than a border colour, so it survives the selected tile's primary border.
- **D-13 One Finding wears the form at a time** (founder ruling 2026-09-01). Across the whole Findings panel exactly one Finding shows its form; every other Finding renders as a row, accepted or not. Three findings keyed in on one zone had been three identical forms, three identical Accept blocks and the recorder line printed three times, with nothing saying which row the advisor was standing in. Creating a Finding opens it, flagging a checklist item opens the Finding it creates, returning to a marked zone opens that zone's first unfinished entry, and accepting closes it — collapsing costs nothing because every field persisted as it was tapped (D-11). A collapsed draft is distinguished from a closed record by its control alone, no extra chip: **Continue**, dashed and lit, against **Edit**, solid and quiet; and its summary line names the reason it cannot be accepted ("no action chosen yet") in amber rather than sitting blank. Hit targets across the inspection screen — damage and action chips, the discard control, the note field, the checklist tri-state — stand at 32px: the screen is used on a tablet beside the car, and 22px chips were not reliably hittable.
- **D-14 A Finding is shown where it was captured** (founder ruling 2026-09-01). Flagging a Service Checklist item still creates a Finding — nothing else can reach a Job, so the domain model is unchanged — but that Finding is rendered **under the checklist row that produced it** and never echoed in the damage list. The Findings panel becomes **Damage findings** and holds Damage Map findings only; its count and empty state speak for damage alone. Marking a wear item at the foot of the page had been making a tile appear several hundred pixels away at the top, so the thing the advisor touched was not the thing that answered, and one item was printed twice on one screen. Each capture surface now owns what it produces. Because the checklist row's tri-state already states the condition, the Finding beneath it never repeats it, and with no damage chips, ordinal or condition to sit beside, its discard control rides on the proposed-action row rather than holding a line of its own. The single-open-form rule (D-13) spans both surfaces: opening a checklist Finding closes an open damage Finding, and the reverse. The case page's Inspection rollup is unaffected — it summarises the whole inspection and still counts both, with checklist findings named as a subset.
- **D-15 Two questions, two named bars** (founder ruling 2026-09-01). The damage and proposed-action chips were two unlabelled rows of identical geometry — eight buttons in a block, with nothing saying that the first answers *what is wrong* and the second *what we will do*, and with two different meanings of "selected" (hatched amber outline above, orange soft fill below). Each question now carries its **name in a fixed label column** and its answers in a **single joined bar** whose cells share the row equally, so both bars align, every option is the same size to hit, and the two rows are told apart by their labels rather than by memory. The unpicked state was the larger fault and was failing outright: `faint` labels measured 3.4:1 against the tile and `border-strong` outlines 1.6:1, so available choices read as switched off. Interactive bars are drawn in `faint` (3.4:1, above the 3:1 floor for controls) with `muted-foreground` labels (7:1), and the **Service Checklist tri-state is drawn the same way** — it is the same control and cannot sit a stop dimmer than its neighbours. Selected cells drop the hatch and carry a tint alone: amber for damage, primary for action; hatch stays with status badges. Cells keep 32px as a floor and grow rather than clip — Thai damage terms wrap to two lines, and the bar stretches every cell to match. The bar's shape does **not** encode cardinality: damage and action are both multi-select (repair *and* repaint is one real job) while the checklist tri-state is pick-one, so the label column and position carry the distinction; a tick inside the selected cell was rejected for reflowing the bar on every tap. Discard leaves the chip rows and joins **Accept** in the footer — they are the two ways a form ends, and keeping it out of the bars lets both run the full width (superseding D-14's placement of it on the action row). Ordinals ride in the label column rather than holding a line.
- **D-16 A Finding claims nothing the inspector did not tap** (founder ruling 2026-09-01). A new map Finding was created holding `["SCRATCH"]` and `["REPAIR"]` — inherited from the M0 mockup — and Scratch could not then be switched off, because the client and the server both floored an emptied damage list back to `["SCRATCH"]`. So a Finding was born asserting a damage and a priced action nobody had chosen, with no dashed styling to mark either as a guess, and Accept carried both through unnoticed. Both lists now start **empty** and either may be emptied while the Finding is being captured. The Accept gate (D-11) widens to match: a map Finding must name **both** what is wrong and what to do about it, because a repaint with no damage behind it prices a panel for no stated reason. Checklist Findings are gated differently, because their tri-state settled the question before the Finding existed: **"due soon" accepts with no proposed work at all**, and only "needs work" is asked what work. Requiring an action of every checklist Finding had stranded the case — a due-soon item could never be accepted, pinning the page at "Open inspection"; and once acceptable it would have pinned at "Group into Jobs" instead, since the only way out of the ungrouped set is acquiring a Job. So the grouping candidate set (`isGroupable`) also withholds any accepted Finding proposing no work, rather than forcing the advisor to raise a Job for work they just recorded as unnecessary. A draft says which half it is still missing, in the row and in the disabled Accept's tooltip, rather than sitting blank. The Damage Map's **selected ring** is likewise put down rather than left standing: it had been set on zone tap and cleared nowhere, so the first zone touched stayed ringed for the rest of the inspection. Tapping the ringed zone again puts it down (closing that zone's open form with it), accepting a Finding drops it, and discarding a zone's last Finding drops it — the ring means "the zone I am working in", never "a zone I once visited".
- **D-17 The tri-state is part of the record it made** (founder ruling 2026-09-02). A Service Checklist row's tri-state stayed live over an **accepted** Finding, so D-11's rule — accepted Findings are records, reopened only by an explicit Edit — held on the damage side and nowhere else. One stray tap rewrote the condition while leaving `confirmedAt` set, walking past the gate that had just been widened; and tapping **OK** deleted the Finding and every photo on it immediately, with none of the arm-then-confirm the damage side's discard requires. The tri-state now locks once its Finding is accepted, and `setChecklistState` refuses on the server too — a disabled button is not where a destructive path gets enforced. Reopening from the record beneath unlocks it. Separately, the Fix bar is offered **per capture surface**: a wear item may be repaired, replaced or serviced, never **repainted**, which is a paint-booth action on a body panel and was nonsense on every row of the checklist. The Damage Map keeps all four.
